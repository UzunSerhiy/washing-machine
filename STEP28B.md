# Шаг 28Б: сохранение аварийной блокировки при перезапуске (REAL)

В REAL создаётся файл состояния `/app/.motion_fault_state.json` (bind mount `./backend:/app`).
Переменная `MOTION_FAULT_STATE_PATH` позволяет указать другой **постоянный** том.
Отсутствующий, повреждённый или неподдерживаемый файл трактуется как **аварийная блокировка**, а не как разрешение движения.

ВАЖНО: При первом запуске после установки патча `motion-fault.latched=true` — это ожидаемое fail-closed поведение. Никакого RUN или автоматического RESET. Для снятия блокировки нужно убедиться в физической остановке, штатном состоянии E-STOP и физическом RESET, затем использовать существующий endpoint `/api/machine/motion-fault/acknowledge` с `{"operator_confirmed_stopped":true}`.

Не удаляйте файл состояния для снятия блокировки: отсутствие файла также блокирует движение. Не изменяйте его вручную. Обеспечьте права на запись для backend. Нельзя хранить файл в /tmp или эфемерном слое контейнера.

Сценарии: сохранение E15 на диск до best-effort STOP; восстановление блокировки после создания нового Machine; атомарное снятие при подтверждении; ошибка записи не снимает блокировку в памяти; некорректный файл блокирует запуск. Физическая E-STOP цепь обязательна. Не является safety-rated системой.

Установка ZIP в корень проекта, тесты `docker compose exec backend python -m pytest -q tests/test_motion_fault_persistence.py` и затем полный `python -m pytest -q`.

Ограничения: сериализация чтений/записей предполагает один backend-процесс; несколько воркеров с отдельными Machine недопустимы. Нельзя считать эту защиту полноценной защитой от гонок RUN/acknowledge. При ошибке записи во время фиксации аварии блокировка удерживается в памяти, а после перезапуска некорректное/старое состояние может быть прочитано; для промышленного применения необходимо гарантировать надёжное хранилище и запрет движения при его недоступности.
